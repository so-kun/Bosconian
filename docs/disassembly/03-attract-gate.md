# アトラクト遷移のゲート（逆アセンブルで特定）

設定画面→アトラクトへ進まない原因を、ローカル逆アセンブル＋実機トレースで特定した。
（ここに残すのは挙動の要約。プログラム本体は `analysis/`（gitignore）にのみ保持。）

## ゲートの正体: フレーム同期フラグ videoram[0x83e1]

- **メインCPU**は 0x3943 で `ei` 後に videoram[0x83e1] を読み、**0xFF の間ループ**
  （0xFF以外になったら抜ける）。
- **サブCPU**も 0x35a で**同一フラグ 0x83e1 を同じ条件で待つ**。
- 実測: 0x83e1 は永久に 0xFF。よって両CPUが同フラグで待ち続ける（フレーム同期の
  ハンドシェイクが成立しない）。

## 解放機構: 0x3fbd のルーチン

```
0x3fbd: videoram[0x8000] = 0x01
0x3fc2: videoram[0x8001]++            ; フレームカウンタ
0x3fc6: if (bit7 of videoram[0x8001]) ; 0x80まで数えたら
0x3fca:   videoram[0x83e1] = 0        ; フラグ解放（両CPUのwaitが抜ける）
```

- このルーチンが呼ばれるとカウンタ 0x8001 が進み、約128回で 0x83e1 を解放する。
- 実測: videoram[0x8001] は **0 のまま**。つまり **0x3fbd が一度も呼ばれていない**。

## なぜ呼ばれないか

- メインの vblank 割り込みは正常（IM1 → 0x38 → `jp 0x1e6`、毎フレーム発火、
  main NMIの誤発火なし）。
- ISRは 0x1e6 から走り、**タスク/ポインタテーブル（0x3f80 付近: 0x8a0c… /
  0x805a… の作業領域アドレス列）を `rst 0x10` で辿るタスクディスパッチャ**を実行。
  Galaga系の task_man と同種の構造。
- ISRの実行経路は 0x3f00 領域まで到達するが、**カウンタ更新/解放タスク（0x3fbd）
  までは到達しない**。0x3f00 付近のタスク処理が、あるタスクを実行する条件を
  満たさず分岐しているため。
- この分岐は主に共有RAMの作業領域（0x7ae2-0x7aeb 等）を参照している。

## 根本原因の見立て

フレーム処理のタスクディスパッチャが、カウンタ/解放タスクを起動していない。
考えられる要因:
1. タスクリスト（作業領域 0x8a0c… / 0x805a…）の初期化が、未実行の起動経路に依存
2. `rst 0x10` を使うタスク呼び出し機構と、共有RAMを介したメイン/サブの協調の
   どこかに、実機と挙動が異なる箇所（ハード状態依存 or 微妙なタイミング）
3. サブCPU側が進めるべき作業領域の値が未更新

いずれも「もう一段のトレース（0x3f00 のタスク処理が参照する条件の特定）」が必要。

## 重要な確認事項（切り分け済み）

- 05XX/50XX/52XX 等**未実装チップの応答待ちではない**（サブは健全、待ちは同一フラグ）
- 06XX→メインNMIの誤発火は**ない**（main NMI=0）
- メモリ整合性は完全（RAM read/write不一致0）、Z80コアは zex 全合格
- よって残る差異は「フレームタスク・ディスパッチャが特定タスクを起動する条件」に
  局在している

## 追記: 完全な連鎖と結論（さらにトレース）

解放条件を末端まで辿った結果、**循環依存**が判明した:

- メインの解放 0x3fbd は 0x3a6f の `jp nz,0x3fbd`（videoram[0x8bc0] の bit7）で分岐。
- videoram[0x8bc0] は**サブCPUが書く**（サブROM 0x75f/0xeb9/0x1d1e）。実測 0x60 で停滞。
- サブは自身の main-line で 0x8bc0 を進めるが、その main-line は 0x35a で 0x83e1 を待機。
- 0x83e1 の解放はメインの 0x3fbd 側（= 0x8bc0 bit7 待ち）。
  → **メインはサブの 0x8bc0 を待ち、サブはメインの 0x83e1 を待つ循環**。

サブの vblank 割り込み（0x38→0x422、毎フレーム発火）は走るが 0x8bc0 を進めない
（0x8bc0 更新はサブ main-line のみ）。実機ではこの循環が特定のCPU間タイミング/
割り込み順序でブートストラップされて解けるが、HLEスケジューラでは解けずに停滞する。

長時間実行（16,000フレーム）の確認:
- 設定画面のテキストは**完全固定**（f2000〜f14000でハッシュ不変）＝アトラクトへ遷移せず
- videoram[0x837a] は**フリーラン・フレームカウンタ**（0x13→0x35→…→0xdb、ラップ）
  ＝毎フレームのループは回っているが、状態機械が進まない

## 結論と意義

- **要件2（起動画面の再現）は実ROMで完全達成**。Z80×3・メモリマップ・タイミング・
  06XX/51XX・ビデオ描画は正しく動作している（強い検証）。
- アトラクト以降の停滞は、**多CPUフレーム同期のブートストラップに関する
  タイミング精度の問題**に局在。これはアーケードHLEで最も難しい部類（MAMEも完全な
  MCUダンプと長年の作業を要した領域）で、解決は高工数・不確実。
- 選択肢: (a) CPU間インターリーブ/割り込み順序の精度を上げてブートストラップを
  狙う深追い、(b) 検証済みの起動基盤を土台に route(c)（src/game/ ネイティブ再実装）へ
  重心を移す、(c) 起動画面までを成果として一旦固める。
