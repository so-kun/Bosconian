# カスタムチップ（06XX / 51XX）のHLE実装と観測

フェーズ3。MB88xx MCUを丸ごと実行するのではなく、**チップの挙動を直接実装（HLE）**する
方針（再実装ルート(c)に合致し、実機ファーム不要）。

## 実装したもの

### 06XX バス（`src/machine/namco06.ts`）
MAME `namco06.cpp`（BSD-3-Clause）の挙動をモデル化:
- コントロールレジスタ: bit[3:0]=チップセレクト、bit[4]=R/!W、bit[7:5]=クロック分周
- データ読み=選択チップの read() のAND、データ書き=選択チップへ write()
- **読み転送中は制御CPUに /NMI をパルス**（1バイト/NMIでクロックアウト）。
  `tick(cycles)` が周期到達でtrueを返し、マシンが該当CPUに NMI を撃つ。
  06xx_0→maincpu（周期64cyc）、06xx_1→subcpu（周期512cyc）

### 51XX I/O・コイン/クレジット（`src/machine/namco51.ts`）
コマンド仕様（`namco51.cpp`）から挙動を再実装:
- 00 nop / 01+4引数 コイン設定 / 02 クレジットモード / 03,04 ジョイ再マップ / 05 スイッチモード
- スイッチモード読み=生入力ニブル、クレジットモード読み=[クレジットBCD, スタート/コイン, P1方向, P2方向]
- vblank毎にコイン/スタートのエッジ処理（コイン→クレジット加算、スタート→消費）
- 入力状態は `machine.input`（ブラウザのキーボードから設定）

## 観測結果（実ROMで検証）

06XX/51XX 統合により、**設定画面で凍結していた状態が解消**:
- 統合前: vram署名が完全固定（メインループが停止）
- 統合後: vram署名がフレーム毎に変化＝メインループ稼働
- **両サブCPUが実行され、共有RAM/videoramへ内容を書き込む**（約6400書き込み/60フレーム）
- vblank IRQ が毎フレーム発火
- **コイン投入でクレジットが加算される**（0→1、51XXのコイン管理が機能）

## 残る論点（次段）

- **設定画面→アトラクトモードへの遷移が未達**。メインCPUは自己テスト画面では 0x7000
  （51XXデータ）を読まない（入力読みは実プレイ/アトラクト時のみ）ので、遷移の
  ゲート要因は別。有力な仮説:
  - サブCPU側の自己テストが 06xx_1 に接続された **50XX_2 / 52XX** の応答を要し、
    未接続（0xff応答）だと「自己テストOK」署名を共有RAMに書かず、メインが待機し続ける
  - → **50XX（演算/プロテクト）と 52XX（音声）のHLEを 06xx_1 に接続**して検証する
- 起動所要フレーム（≈815f）の実機/MAME比の妥当性検証（別途）
