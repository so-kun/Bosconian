# ボスコニアン（Namco, 1981）Web完全再現 — 調査レポート＋実装計画

## Context

ナムコのアーケードゲーム「ボスコニアン」を、ROMからの逆アセンブルを起点に、グラフィック・挙動・サウンドまで含めてWeb上で完全再現したい。さらに、ページ表示時には実機に電源を入れたときの起動画面から再現したい。本リポジトリは現在空であり、ゼロから構築する。

本ドキュメントは、(A) 実現可能性の調査結果と (B) それに基づく実装計画をまとめたもの。

---

# A. 調査レポート

## 結論（先に要点）

| 要件 | 判定 | 根拠 |
|---|---|---|
| グラフィックの完全再現 | **可能** | ビデオ回路が完全に文書化済み。タイル/スプライト/ドットのビットレイアウト、カラーPROMの抵抗値、星空生成の16bit LFSRまで判明 |
| 挙動（ゲームロジック）の完全再現 | **可能だが最大の工数** | ボスコニアン専用の公開逆アセンブルは**存在しない**。Z80プログラム計28KB×3CPUをゼロから解析することになる |
| サウンドの完全再現 | **部分的に困難** | 3系統ある。WSGは容易、52XX音声は中程度、**54XX＋ディスクリートの爆発/ショット音が最難関**（回路図由来のFPGA再現ですら未解決） |
| 起動時表示の再現 | **可能。ただし方式に依存** | ROMを実行するエミュレーション方式なら自動的に得られる。逆アセンブル由来の再実装では「模写」にしかならない |
| ROMの同梱配布 | **不可（高リスク）** | 米国 約2076年、日本 約2051年まで著作権保護。バンダイナムコは現に権利行使中 |

**総合判定: 技術的には実現可能。ただし「ROMをリポジトリに同梱する」ことだけは明確なNGライン。**

## 1. ハードウェア仕様（確定 / 一次情報）

MAMEドライバとMiSTerのFPGAコアという**独立2実装が完全に一致**しており、仕様は確定していると見てよい。

出典（すべて **BSD-3-Clause**。GPLではないため参照・流用の自由度が高い）:
- `mamedev/mame` `src/mame/namco/galaga.cpp` — ドライバ本体・ROM定義・マシン構成（© Nicola Salmoria）
- 同 `src/mame/namco/bosco.cpp` — ビデオ
- 同 `src/mame/namco/starfield_05xx.cpp` — 星空生成05XXの**実チップ解析による完全RE文書**（© Robert Hildinger, 2019）
- 同 `src/devices/sound/namco.cpp` — WSG波形音源
- 同 `src/mame/namco/namco50/51/52/54/06.cpp` — カスタムチップ
- `MiSTer-devel/Arcade-Bosconian_MiSTer` `rtl/bosconian.vhd`（GPLv2、Midwayサービス回路図由来）

### 基本構成
| 項目 | 内容 |
|---|---|
| CPU | Z80 ×3、各 3.072 MHz（MASTER_CLOCK 18.432 MHz ÷6） |
| CPU間 | 全CPUが**同一メモリマップを共有**（`0x0000-0x3fff` のROMのみ各CPU別）／共有RAM `0x7800-0x7fff` |
| 画面 | 288×224 表示、384×264 総ドット、ピクセルクロック 6.144 MHz → **60.606 Hz** |
| 音源 | Namco WSG 3ch 波形テーブル（96 kHz = 18.432M/6/32） |

### カスタムチップ（CPUボード / ビデオボードに二分）
- **CPUボード**: 06XX（5xXXバスI/F）, 07XX（クロック分周）, 08XX×3（バスコントローラ）, 50XX（演算/プロテクト）, 51XX（I/O）, 54XX（爆発音）
- **ビデオボード**: 03XX×2（機能不明）, 05XX（星空）, 06XX, 07XX, 50XX, 52XX（音声再生）

**重要**: 50XX/51XX/52XX/54XX は**富士通 MB88xx 系 4bit MCU の実チップ**であり、MAMEはそのファームウェアROMを実行して再現している（`50xx.bin` 2KB / `51xx.bin` 1KB / `52xx.bin` 1KB / `54xx.bin` 1KB）。つまり**ROM依存はZ80プログラムROMだけではない**。

### メモリマップ（`bosco_map`）
```
0000-3fff ROM (CPUごとに別内容)
6800-6807 R  DSW
6800-681f W  Namco WSG サウンドレジスタ
6820-6827 W  misclatch (LS259): irq1clr / irq2clr / nmion / sub&sub2 RESET
6830      W  watchdog reset
7000-70ff RW 06xx_0 データ (51XX / 50XX_1 / 54XX)
7100      RW 06xx_0 コントロール
7800-7fff RW 共有RAM
8000-8fff W  videoram (+スプライトレジスタ)
9000-90ff RW 06xx_1 データ (50XX_2 / 52XX)
9100      RW 06xx_1 コントロール
9800-980f W  radarattr
9810      W  scrollX
9820      W  scrollY
9830      W  starcontrol   (bit0-2=X速度, bit3-5=Y速度)
9840      W  starclr（書き込みで星空ON）
9870-9877 W  videolatch (LS259): Q0=flipscreen, Q4/Q5=星空バンク, Q7=50xx_2/52xx reset
```

### 描画レイヤ（`screen_update_bosco` の順序）
1. 黒クリア
2. **星空**（05XX の16bit LFSR）— プレイフィールド領域のみ
3. **スプライト 6個のみ**（`videoram[0x03d4]` から2バイト×6、16×16、2bpp）
   → プレイヤー機＋敵編隊5機に対応。基地・小惑星などはBGタイルマップ側
4. **BGタイルマップ** 32×32（プレイフィールド、左28文字にクリップ、scrollX/Y）
5. **FGタイルマップ** 8×32（右端のレーダー帯、28文字目以降）
6. **弾/レーダードット**（`radarattr` 経由、4×4ドット、12個）
7. 水平オフセット221-223をスキップする補正（レーダーを3px左へずらす）

### ROMセット（`bosco` = version 5）— `galaga.cpp` を直接読んで確定
> 注: 調査エージェントはこの構成の主張を「否決」したが、**否決の方が誤り**。`ROM_START(bosco)` を直読して確認済み。誤りだったのは「プログラム計約7KB」という部分で、正しくは **4KB×7 = 28KB**。

| 領域 | ファイル | サイズ |
|---|---|---|
| maincpu | `bos5_1.3p` `bos5_2.3m` `bos5_3.2m` `bos5_4.2l` | 4KB×4 |
| sub | `bos5_5.3f` `bos5_6.3j` | 4KB×2 |
| sub2 | `bos1_7.2c` | 4KB |
| gfx1（char 8×8 2bpp） | `bos1_14.5d` | 4KB |
| gfx2（sprite 16×16 2bpp） | `bos1_13.5e` | 4KB |
| gfx3（dots 4×4） | `bos1-4.2r` | 256B |
| proms | `bos1-6.6b`(32B パレット) `bos1-5.4m`(256B LUT) `bos1-3.2d` `bos1-7.7h` | |
| namco（WSG波形） | `bos1-1.1d` `bos1-2.5c` | 256B×2 |
| 52xx（デジタル音声） | `bos1_9.5n` `bos1_10.5m` `bos1_11.5k` | 4KB×3 |
| MCUファーム（デバイス側） | `50xx.bin` `51xx.bin` `52xx.bin` `54xx.bin` | 2KB + 1KB×3 |

リビジョン: `bosco`(v5) / `bosco3`(v3) / `bosco1` / `bosco1o` / `boscomd` / `boscomdo`（Midwayライセンス版）

### MAME自身が記録している未解決点
- **水平解像度**: 「実は285ではないか」というTODO。現行は288で描画。PCB映像では右ボーダーがわずかに広い
- **波形PROMが2種類**: `prom.1d` と `bosco.spr` のダンプがあり「音楽が大きく変わる」。MAMEは他のNamco作品との類似から `prom.1d` を採用
- **06XXタイミング**: 元プログラムの `0BB1` 番地に `ex af,af'` でコマンドが壊れるバグがあり、MAMEは06XXのNMI生成を十分速くすることで回避している

## 2. サウンド — 3系統に分かれる（最重要の難所）

| 系統 | 内容 | 難易度 |
|---|---|---|
| **Namco WSG** | 3ch 波形テーブル音源。256B×2のPROMに波形。CPUから `6800-681f` のレジスタで制御 | **低**。Web Audio の AudioWorklet で素直に実装可能 |
| **52XX 音声** | MB8843 MCUが 12KB のデジタイズド音声ROM（`bos1_9/10/11`）を再生。「Blast off」等 | **中**。MCU＋DAC＋555外部クロック（33k/10k/0.0047µF）のモデル化が必要 |
| **54XX ＋ ディスクリート** | MB8844 MCUがノイズ生成、その出力をアナログ・ディスクリート回路で加工。爆発音・ショット音 | **高（最難関）**。回路図由来のFPGA実装（MiSTer core）ですら未解決 |

MiSTer core の Known Issues（2025/12時点のmasterでも残存）:
> Shot and explosion sounds are not working perfectly / Base explosion sound is not nearly loud enough / Shot sound changes pitch from shot to shot

→ **「サウンドの完全再現」を額面通り達成した実装は世界に存在しない。** 目標としては「WSGと52XX音声は完全、54XX系は近似」が現実的な到達点。

## 3. 逆アセンブル — ボスコニアン専用資料は存在しない

- **ボスコニアンの公開逆アセンブルは確認できなかった。** ゼロからの解析になる。
- ただし**同じGalaga系ハードのGalagaには完全な前例がある**: `neiderm/arcade`（フォークが `hackbar/galaga`）は再アセンブル可能なASxxxアセンブリソースで、Z80プログラムROM全24KBを**バイト一致で再構築**できる。全16,614行中 `.db/.dw` は約995行のみ = 実質的にコード解読済み。
  - `gg1-3.s` = 敵編隊・攻撃隊列・ボス/捕獲、`gg1-4.s` = ハイスコア・**電源投入時メモリテスト**・サービスモード、`task_man.s` = RST 38（V-blank）起動の60Hz 32エントリ・タスクディスパッチャ
  - → **個人規模で達成可能であることの実証**。ただしライセンスは "non-commercial purpose"、また上流は2020年5月以降停止。
- 解析ワークフローは道具化済み。`Justin-Credible/pac-man-emulator` はメモリアドレスをキーとする外部注釈ファイルを読み、逆アセンブラ生成の擬似コードと人手注釈をF11で切り替える対話デバッガを実装している。MAMEデバッガの `comadd`（`.cmt` に永続化）や Ghidra も等価。

## 4. 起動時の表示

Galaga系基板の実機修理ログによる起動シーケンス（arcade-museum フォーラム、Arcade Otaku Wiki）:

```
電源投入 → 白いブロック状の画面
        → グリッド（クロスハッチ）等の中間画面
        → CPU1 が RAM テスト → "RAM OK" 表示
        → CPU2/CPU3 の /RESET を解放、各自ROMをチェックし共有RAMへ結果を書く
        → "ROM OK" 表示
        → アトラクトモード
```
（"RAM OK" で固まるのは CPU1 が他2CPUの書き込みを待っている状態、という故障診断が成立することからも構造が裏付けられる）

**ここが方式選択を決定づける**:
- **エミュレーション方式なら、この画面は「実装する」ものではなく実ROMを走らせれば勝手に出る。** しかも自己診断ルーチンが通ることが、こちらのハードウェア実装の正しさの検証になる。
- **再実装方式では、この画面は別途の解析対象**であり、再現しても「模写」にとどまる（RAM/ROMを実際に検査していないため）。Galagino が `-p` オプションで RAM/ROMテストを**無効化するパッチ**を当てていることからも、再実装側では邪魔物として扱われるのが通例とわかる。

**要件2（起動時表示の再現）と、ご指定の方針（逆アセンブルからの再実装）は、厳密には両立しません。** 後述の推奨アプローチで両立させます。

## 5. 法務

### (a) ROMイメージの配布 — **明確なNG**
MAMEdev自身の公式見解（`docs/source/whatis.rst`、MAME Documentation 0.289 / 2026年時点で現存）:
> ROM, CD, hard disk and other media images are all copyrighted material. They may not be lawfully distributed without the explicit permission of the copyright holder(s). **They are not "abandonware", nor has copyright expired** on any of the software supported by MAME.

- 米国: 17 U.S.C. §302(c) 職務著作 = 公表後95年 → **約2076年まで**
- 日本: 2018年TPP改正後、法人著作物70年 → **約2051年まで**
- 権利者は現に権利行使中: **Arcade Archives BOSCONIAN**（HAMSTER、2023/08/24、PS4/Switch、© Bandai Namco Entertainment Inc.）
- MAMEが許諾を得て配布している無償ROM（Gridlee等）ですら「MAMEサイト上でのみ」に限定され、自製ソフトへの同梱は禁止。ボスコニアンはそこに含まれない。

**→ 「MAMEなどから参照できないか」という点への回答: MAMEプロジェクトはROMを配布しておらず、参照経路として使えません。** また本セッション環境では archive.org がプロキシで403遮断されており、自動取得もできません。

### (b) 逆アセンブル・リバースエンジニアリング
相互運用性を目的としたリバースエンジニアリングは、米国では判例上フェアユースとして認められてきた領域（Sega v. Accolade 等）。ただし**成果物が元コードの表現を取り込めば別問題**。日本法にも同種の明文の安全地帯はない。

### (c) 業界標準の分離モデル — **これが唯一の現実解**
> **再現物（HDL/エミュレータ）はオープンソースで配布し、著作物であるROMは配布せず利用者が用意する**

実例:
- **MiSTer ボスコニアンcore**（GPLv2）: Readme に "ROMs are not included. In order to use this arcade, you need to provide the correct ROMs."、MRAファイルでチェックサムを指定し `/games/mame/<mame rom>.zip` を参照。同一の免責文が MiSTer 全体の規約として明文化されている。
- **Galagino**（ESP32向けGalaga系再実装）: `roms/` ディレクトリには `.gitignore` と `README.md` のみ（バイナリ0）。Pythonスクリプトで利用者が自前ROMを変換してスケッチにパッチ。

**限定事項**: これは業界慣行であって司法判断を経たセーフハーバーではない。利用者側のROM入手自体は通常侵害にあたる。Internet Archive の Internet Arcade のようにROMを直接配信する運用も現に存在するが、それは慣行の反例であって適法性の証明ではない。

### (d) 正規ライセンス
バンダイナムコから個人/小規模プロジェクトがクラシックタイトルのWeb配信ライセンスを得られるかは**未確認**。既にArcade Archives（HAMSTER）とNamco Museumで商用展開中であるため、競合になる点は不利材料。

> 以上は条文とMAMEdevの立場表明からの一般的整理であり、法的助言ではありません。

## 6. 実装手段の比較

| | 精度 | 工数 | 法的リスク | 起動画面 |
|---|---|---|---|---|
| **(a) MAME/EmulatorJS流用** | 高 | 極小 | 中（ROMをどう渡すか次第）＋GPL | ○ 自動 |
| **(b) 自前ハードウェアエミュレータ** | **最高** | 大 | 低（ROM非同梱なら） | ◎ 自動、かつ検証手段になる |
| **(c) 逆アセンブルからJS再実装** | 中〜高 | **最大** | 低〜中 | △ 模写のみ |

- **(a)** EmulatorJS + mame2003 コアは設定数行でブラウザ起動可能。ただし `EJS_core` の記法は流動的（v4.0.10 で `mame2003` → `mame` にリネーム、既定コアも `mame2003_plus` に変化）。さらに **MAME 0.78 の `bosco.c` は外部サンプルセット前提**で、EmulatorJS は単一zipしか渡さないため**一部の音が鳴らない**。「ブラウザで動く」は成立するが「完全再現」は成立しない。
- **(b)** Web Audio（AudioWorklet）でのWSG実装は確立された領域。星空05XXは完全RE済みなのでLFSRをそのまま移植可能。
- **(c)** ボスコニアン版の解析資料が皆無のため、28KB×3CPUの解析が丸ごと工数として乗る。Galagaの前例（16,614行）から見て**数ヶ月規模**。

# B. 実装計画

## 推奨アプローチ: (b) を土台にして (c) を載せるハイブリッド

ご指定は「(c) 逆アセンブル結果から再実装」ですが、**(c)単独では要件2（起動時表示の再現）が原理的に模写にしかならず、また逆アセンブル作業そのものが実行環境なしには進みません。** そこで:

1. **まず (b) 自前ハードウェアエミュレータを作る。** これが同時に、
   - 要件2（起動時セルフテスト画面）を**そのまま満たす**
   - 逆アセンブル作業のための**トレース/デバッグ環境**になる
   - 自分のハード実装の正しさを、実ROMの自己診断ルーチンが**自動で検証してくれる**
2. **その上で (c) の逆アセンブル・再実装を進める。** エミュレータのトレースと突き合わせながら段階的にJS実装へ置き換えられるので、「完全一致しているか」を常に検証できる。
3. 最終的に、**同一UIから「エミュレーション実行」と「ネイティブ再実装」を切替可能**にする。前者が正解データ、後者が成果物。

ROMは**同梱せず、ユーザーがブラウザで読み込む**（MiSTer / Galagino と同じ分離モデル）。

## 検証方法

1. **Z80コア**: `zexall` / `zexdoc` 命令エクササイザ（実機由来のチェックサムと照合、8000+ケース）をブラウザ上で走らせる
2. **ハードウェア実装**: **実ROMの電源投入時セルフテスト（RAM OK / ROM OK）が通ること**が最も強力な自動テスト。ROM自身がこちらのハードを検査してくれる
3. **ビデオ**: 実機PCB映像・MAMEスクリーンショットとのピクセル比較（レーダーの3pxシフト、右ボーダー幅がチェックポイント）
4. **カスタムチップ**: 06XXのNMI生成が十分速いこと（`0BB1` のバグを踏まないこと）を、CPU1がハングしないことで確認
5. **再実装（フェーズ6）**: `tools/trace-compare/` で、同一入力列に対するエミュレータ実行と再実装のフレームごとの状態を突き合わせる

## リスクと未解決事項

| リスク | 対応 |
|---|---|
| **ROMをユーザーが用意できない** | 分離モデル以外に安全な手段がない。UI上で明示し、`README` に MiSTer 準拠の免責を置く |
| **54XX＋ディスクリート音の完全再現** | 世界的に未達。近似実装とし、「完全再現できていない箇所」としてドキュメント化する |
| **フェーズ5の逆アセンブル工数** | Galagaの前例（16,614行）から数ヶ月規模。フェーズ0-4が単独で成果物として成立するよう設計する |
| **水平解像度 288 vs 285** | MAMEでも未解決。288で実装し、切替オプションを持たせる |
| **波形PROM 2種問題** | `prom.1d`（MAME採用）を既定とし、`bosco.spr` も選択可能にする |
| **MiSTer VHDLの参照** | GPLv2。**仕様の裏取りにのみ使い、コードは移植しない**（BSD-3-Clauseの MAME 側を実装の根拠にする） |
